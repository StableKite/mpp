# Rockchip Media Process Platform (MPP)

**Язык:** Русский | [English (original)](readme.txt)

## Особенности сборки этого форка

По умолчанию CMake собирает MPP в режиме `Release` с `-O3 -DNDEBUG`, а предупреждения компилятора считаются ошибками (`WARNINGS_AS_ERRORS=ON`). Полный набор кодеков и видеопроцессоров, включая VDPP и H.264 fast-play-once, включён по умолчанию.

Для обычной переносимой сборки дополнительная CPU-специфичная оптимизация отключена. Если сборка выполняется непосредственно на целевой машине и полученный бинарный файл не требуется переносить на другой процессор, её можно включить явно:

```bash
cmake -S . -B build -DMPP_ENABLE_NATIVE_OPTIMIZATION=ON
cmake --build build --parallel
```

При этом для GCC/Clang добавляется `-march=native`. Опция намеренно запрещена при кросс-компиляции.

## Структура модулей

- **MPP** — Media Process Platform, платформа обработки мультимедиа.
- **MPI** — Media Process Interface, интерфейс обработки мультимедиа.
- **HAL** — Hardware Abstraction Layer, слой аппаратной абстракции.
- **OSAL** — Operating System Abstraction Layer, слой абстракции операционной системы.

## Правила проекта

### 1. Размещение заголовочных файлов

1. Каталог `inc` внутри каждого модуля предназначен для заголовочных файлов, используемых другими модулями.
2. Внутренние заголовочные файлы модуля должны располагаться рядом с соответствующей реализацией.
3. Заголовочные файлы не должны содержать относительные или абсолютные пути. Все пути поиска заголовков должны задаваться системой сборки.

### 2. Система сборки

1. Для кроссплатформенной сборки используется CMake.
2. Следует использовать out-of-source сборку CMake; итоговые бинарные файлы и библиотеки устанавливаются в каталог `out/`.

### 3. Порядок подключений в исходных файлах

1. `MODULE_TAG`.
2. Системные заголовочные файлы.
3. Заголовочные файлы OSAL.
4. Заголовочные файлы модуля.

## Примечания

1. Поддержка Windows больше не сопровождается.
2. MPP поддерживает все актуальные семейства Rockchip, включая:
   - RK29XX / RK30XX / RK31XX;
   - RK3288 / RK3368 / RK3399;
   - RK3228 / RK3229 / RK3228H / RK3328;
   - RK3528 / RK3528A;
   - RK3562;
   - RK3566 / RK3568;
   - RK3588;
   - RV1108 / RV1107;
   - RV1109 / RV1126.
3. MPP поддерживает все форматы, поддерживаемые аппаратной частью, кроме VC-1.
4. Репозитории проекта:
   - официальный GitHub: <https://github.com/rockchip-linux/mpp>;
   - GitHub разработки: <https://github.com/HermanChen/mpp>;
   - Gitee разработки: <https://gitee.com/hermanchen82/mpp>.
5. Формат сообщений коммитов должен основываться на рекомендациях <https://keepachangelog.com/en/1.0.0/>.

Дополнительная документация: <http://opensource.rock-chips.com/wiki_Mpp>

## Иерархия Media Process Interface

`MpiPacket` и `MpiFrame` — структуры данных ввода/вывода потока. `MpiBuffer` инкапсулирует разные реализации буферов, например Linux dma-buf и Android Ion. Эта часть архитектуры основана на подходах FFmpeg.

```text
                +-------------------+
                |                   |
                |        MPI        |
                |                   |
                +---------+---------+
                          |
                          |
                          v
                +---------+---------+
                |                   |
            +---+        ctx        +---+
            |   |                   |   |
            |   +-------------------+   |
            |                           |
            v                           v
    +-------+-------+           +-------+-------+
    |               |           |               |
    |     packet     |           |     frame     |
    |               |           |               |
    +---------------+           +-------+-------+
            |                           |
            |                           |
            |                           |
            |     +---------------+     |
            |     |               |     |
            +---->+     buffer    +<----+
                  |               |
                  +---------------+
```

## Пример работы декодера H.264

Видеопоток сначала ставится в очередь слоем MPI/MPP. Затем MPP передаёт поток в слой codec, где заголовки разбираются и преобразуются в стандартное представление протокола. Это представление передаётся в HAL, который формирует набор аппаратных регистров и взаимодействует с видеоблоком. После завершения аппаратной задачи результат возвращается обратно: MPP уведомляет codec о завершении обработки, а codec выдаёт декодированный кадр в порядке отображения.

## Режимы использования памяти декодером

Декодер поддерживает три режима работы с памятью.

### Режим 1: полностью внутреннее управление

В этом режиме пользователь **не** вызывает `MPP_DEC_SET_EXT_BUF_GROUP`. Для продолжения работы декодера достаточно вызвать `MPP_DEC_SET_INFO_CHANGE_READY`. Декодер самостоятельно создаёт внутренние буферы, а пользователь должен освобождать каждый полученный кадр.

**Преимущества:**

- проще всего начать работу и быстро получить функционирующий пример.

**Недостатки:**

1. Буферы декодера могут не быть возвращены до его закрытия, из-за чего возможны утечки памяти или сбои.
2. Пользователь не контролирует объём памяти декодера: декодер работает без внешнего лимита и может занять всю доступную ему память.
3. Такой режим плохо подходит для zero-copy вывода изображения.

### Режим 2: частично внутреннее управление

Именно этот режим используется текущим `mpi_dec_test`. Пользователь создаёт `MppBufferGroup` на основе `MppFrame`, возвращённого при изменении параметров потока. Для ограничения потребления памяти можно использовать `mpp_buffer_group_limit_config`.

**Преимущества:**

1. Относительно прост в использовании.
2. Пользователь может освободить `MppBufferGroup` после закрытия декодера, поэтому время жизни памяти можно безопасно контролировать отдельно.
3. Объём памяти можно ограничить через `mpp_buffer_group_limit_config`.

**Недостатки:**

1. Ограничение количества буферов остаётся не полностью точным; объём выделяемой памяти всё ещё жёстко связан с буферами.
2. Реализовать zero-copy вывод также сложно.

### Режим 3: полностью внешнее управление

В этом режиме пользователь создаёт пустой `MppBufferGroup` и импортирует в него память внешнего аллокатора по файловому дескриптору.

В Android буферы создаёт SurfaceFlinger. Затем mediaserver получает файловые дескрипторы от SurfaceFlinger и добавляет их в `MppBufferGroup` декодера.

**Преимущества:**

1. Наиболее эффективный вариант для zero-copy вывода.

**Недостатки:**

1. Наиболее сложный режим для изучения и использования.
2. Архитектура проигрывателя может ограничивать возможность его применения.
3. Для определения корректного размера буфера внешнего аллокатора может потребоваться внешний парсер.

## Расчёт необходимого размера буфера

Для пиксельных данных:

```text
hor_stride * ver_stride * 3 / 2
```

Для дополнительной информации:

```text
hor_stride * ver_stride / 2
```

Таким образом, общего размера

```text
hor_stride * ver_stride * 2
```

будет достаточно.

Для H.264/H.265 обычно достаточно более 20 буферов. Для остальных кодеков обычно достаточно 10 буферов.
